# HyperMaker Design

Product and domain source of truth. Implementation architecture belongs in `impl.md`.

## Product

HyperMaker is a local-first node canvas. Codex turns directly connected artifacts into new reproducible artifacts. Initial types: `text`, `image`, `audio`, `video`.

## Workspace

One active workspace is open at a time. Default workdir is `.hypermaker`; opening another directory switches to it. Opening is a single switch: the path and the cards change together, and an open that fails (a file where a directory was meant, a directory that cannot be written) leaves the workspace that was open exactly as it was, with the reason given. A run belongs to the workspace it was started in - another workspace's cards never show it, refuse Generate because of it, or inherit its result - and a run still going in a workspace is still stoppable after switching away and back. An open shows the outcomes that had already finished by the time it answers, including a run that finished while the open was in progress. `<workdir>/workspace.yml` is the only graph persistence, and it includes each node's last run status and error so a failure is not forgotten on restart. Node IDs are integers; inputs are ordered integer IDs. Input display names always come from source artifact filename. Node files live in `<workdir>/<id>/`; filenames are relative to that node directory.

Downloading a take saves it under the take's own version (`film-v2.mp4`). The card's title is deliberately the same for every take of one card, because the version is shown beside it on screen - which is enough while the files are on the canvas and not enough once they leave it: three cuts of one film arrived in a downloads folder as three `film.mp4`. A file with no version - an imported constant - keeps the name it already had.

Draft nodes have no directory until Generate. A file the person supplies is copied into its new node directory. Supplied files are constant nodes: no method and no Generate. A person brings one in from the canvas - **+ File**, or dropping one or more files on empty canvas - which is the same act as `POST /api/import` with a path on this machine, except that the bytes come from the browser rather than from the server's own disk. The name the browser sends is kept as the card's artifact after being reduced to a base name and to characters no filesystem reads as structure; an upload never chooses its own path. Generated nodes have optional script, artifact, `AGENTS.md`, and raw `codex.jsonl`. No manifest, recursive import discovery, copy-on-link, or simultaneous workspaces.

Dropping a file on a supplied card **replaces that card's material**: the file the card held becomes a kept version, the new bytes are published under the card's next number, and the links and everything recorded about them stay as they were. That is the gesture "this scene, but with my photo instead", and it costs no model. A card a method produced is not replaced this way - its bytes are that method's output, so handing it a file would claim the method made it; the refusal says to bring the file in as its own card and link it from there. A wrong kind of file is named before the method is, because a picture dropped on a film card is the mistake the person can see.

A card keeps its finished versions. Changing the material upstream and pressing Generate again must not cost the artifact already approved, so a run does two things in a fixed order: it freezes a copy of each direct input into `<workdir>/<id>/versions/` and hands the agent those copies, and on success it publishes its output under a fresh name in `versions/` and points the card at that. Nothing the agent writes is visible until the run succeeds, so a failure has nothing to roll back, and the artifact on the card and the materials recorded for it always describe the same bytes.

A run may only publish a file it wrote itself. An agent that names a path left by an earlier run - which a real one did, producing two "versions" of the same video for two different posters - is a failed run with a reason the person can act on, not a new version. The judgement is "was this file written during this run", and it is made without a clock: every file in the node directory is fingerprinted (device, inode, size, nanosecond mtime and ctime) before the run, and the named artifact must no longer match. Comparing modification time against the run's start *with a tolerance* was the first attempt and was wrong twice over: the tolerance had to be large enough for filesystem timestamp granularity, which meant two runs closer together than the slack let the earlier file through as the new result - change a prompt and press Generate again within a second and it happened every time. A fingerprint has no such window. It also leaves the opposite case alone: a deterministic renderer that produces identical bytes twice did write the file, so it is a second version, not a stale one.

What the fingerprint cannot see: an agent that rewrites a file *and* restores it to the
same bytes with the same size within the same timestamp tick of a coarse filesystem -
FAT, some SMB mounts, a few container overlays. The check would call that unwritten and
refuse a legitimate result. The failure is the safe direction (a retryable error, never a
duplicate version), and on the filesystems this runs on the nanosecond clock makes it
practically unreachable; it is written down because "never" would be a claim the check
does not earn. `workspace.yml` stores the kept versions with their source copies, so they survive a restart. Going back to an earlier version is a pointer move, is itself reversible, and is refused while the card is generating.

An instruction is provenance too. A card has two prompt fields: `prompt` is what the person is asking for next and stays theirs to edit, and `promptUsed` is what the artifact on the card was actually made from. They are separate because editing the text does not change the artifact on screen, and one field for both made an edit rewrite the history of an approved take; the replaced version's record was read from the box when the next run started. Each kept version carries its own `prompt`, and restoring a version restores its prompt with its bytes, so the box always describes the picture next to it. A version kept before prompts were recorded has `null`, and that travels with it: restoring such a version clears `promptUsed` rather than leaving the replaced take's instruction on the card, while `prompt` - the next take being written - is left alone, since a restore is not the moment to discard it. The card then reads `asked for: unknown (kept before prompts were recorded)`, because silence reads as agreement. Filling an unknown in with the card's current prompt would be the same lie in the other direction.

Two takes of one card can be compared without choosing between them: a `compare` button on the kept row opens both simultaneously, one pane per version, each captioned with its version, its prompt and the frozen materials it was made from, and either pane can be pointed at any other version. Each material is named with its own card's publish ordinal (`poster.png (v1)`), because a material card keeps one filename across its takes and the version is the only thing that tells two takes apart. It reads from the same node record and file endpoint as the card, and it never restores anything - what the card shows is unchanged when it closes. Only one player sounds at a time: starting one pauses any other sound on the canvas, so two narrated takes can be told apart by ear rather than only by picture. The rule holds between the two panes, and between a pane and a card preview left playing behind the panel. The canvas shows `asked for: …` under the prompt while the box and the artifact disagree, and puts each version's prompt in its tooltip. `made from …` describes the artifact on the card; while the card's live links would freeze different material than the artifact was made from, the card also says `next Generate uses …` and names it, so the next press is stated before it is taken rather than discovered afterwards. Both lines are silent when they would only repeat the artifact's own description.

A published name carries the card's publish ordinal, counted from the files in `versions/`: `v1-`, `v2-`. It is not derived from the version list (restoring empties a slot there, which once made a publish overwrite the artifact on the card) and not from filename collision (an agent naming each render freshly, as the video guide asks, produced `v1-shot-a` and `v1-shot-b` for two takes of one card).

## Canvas

Double-click empty canvas, or press **+ Card**, to create a generation node. Cards drag; canvas pans by dragging empty space and zooms with the wheel, anchored at the pointer. Artifact preview uses a 4:3 aspect ratio that reserves its space, so long text scrolls inside the card instead of pushing Delete and Generate off screen. Dragging A onto B's title bar creates input A on B; the source then returns to where it started. A drag that ends anywhere else keeps its new position, so cards can also be stacked on purpose. Only the primary button starts a drag or a pan. Dragging continues for the complete pointer gesture even when the pointer leaves the card title bar, and ends on pointerup or pointercancel. Links are directional arrows drawn in canvas coordinates, so they stay on their card edges through pan, zoom and drag. Links leaving one card are drawn from different points along its edge, fanned around the header line, so several links to cards at the same height are several distinguishable lines rather than one - a person removes a link by right-clicking it, and a right-click on a line that is four links cannot say which one it means. The fan is measured in world units, so it does not change with zoom, and it stays inside the header band so it is never below a card's visible top.

A link's offset is decided against *both* ends, not just one: it must be separated from the card's other outgoing links and from the target's other incoming links. Separating only one end leaves the commonest canvas there is broken - one text card feeding a narration and a film, all at one height, where the two links share a source and ran on top of each other for their first stretch. No two links share an anchor at either end.

A right-click removes the link *nearest the pointer*, not the one whose hit area happens to be painted last, and the card-free part of the canvas is where a person aims. Where overlapping strokes make the two answers differ, distance wins, and the canvas says which link it removed, naming both ends by card and by the artifact each holds (`Removed the link card #1 text.txt (v1) → card #2 narration.wav (v1).`). Both ends, because two links out of one card are two different actions and a sentence that reads the same for both is not a receipt - a supervisor removed each of two links from one text card and got `card #1` twice. A hit path carries which link it is and no behaviour of its own: one listener decides, or the rule is not a rule - which is exactly how a right-click nearer one link came to remove another. Panning moves the canvas and wheel zoom anchors at the pointer. Right-click a link cancels it and suppresses the browser menu; this still works when the link runs behind another card's body, and right-clicking a card's own control (prompt, select, Generate, Delete) never unlinks anything. Clicking any card raises it to the front, the raised card stays in front across server refreshes, and a covered card can be raised from its exposed edge so its own controls then accept input. Prompts save on a short debounce, on blur, and before Generate; a refresh never overwrites text being typed. Each card has a Delete button; clicking it asks for confirmation, then deletes. Reset layout reflows every card into a four-column grid with fixed spacing (no dependency layering yet).

## Generation

One Generate button produces one exact artifact, and one card has at most one run at a time: a second Generate while a card is running is refused, not queued. The card counts as running from the moment the press is accepted - including the preparation before any agent exists - so two browsers pressing together start one run and are billed once, and Stop always has exactly one target. Generation is asynchronous and concurrent across cards. Start persists workspace and creates node directory; completion persists returned filenames and refreshes only that node. Agent returns only `{script?, artifact}`. Harness validates node-local paths and artifact type. Agent runs with repository root cwd so `.agents` loads, and writes only in a run directory of its own (`<workdir>/.runs/<id>/<start>`), never in the card's.

A card's directory is the person's. Before a run starts, every file in it is copied beside the run and hashed; after the run - success, Stop, failure, or the next startup when the server died - each file is checked by content and put back if it was deleted or changed, and the card says which file had to be restored. The copy is a copy rather than a hardlink because an ordinary save reopens the existing file and writes into it, which a shared inode would not reveal. A file over 64 MiB is kept by a link rather than a copy: a deletion is still repaired and an in-place rewrite is not, and that is said on the card before the agent starts. A stopped run stays `cancelled` even when its damage had to be repaired; a run that succeeded but touched the card is reported as an error, because its output was made from material it modified.

A `two-act` text card takes two linked pictures in order and a creative intent, and drafts one short English voiceover line per picture. A creator can edit the draft locally and make a new version before turning it into narration and a film. Editing does not rewrite the model's version or change the pictures and their links.

A running card shows its state and offers Stop. Stop ends the agent and every process it started, then leaves the card `cancelled` with the previous artifact intact. A failed run leaves the previous artifact intact too and shows its reason on the card; the reason is stored, so it is still there after reopening the page or restarting the server. A run that was cut off by the server stopping is shown as interrupted, never as a draft that never started. A missing agent is reported as an install-or-configure instruction.

Prompt sections, exact order:

```text
# SHARED PROMPT
# OUTPUT TYPE
# GENERATION METHOD
# QUALITY
# AGENTS
# INPUTS
# CONTEXT
# USER PROMPT
```

Direct inputs include directory; the frozen copy's path plus the artifact filename it came from, text contents or multimodal metadata; source filename and contents when present; and `AGENTS.md` when present. Only direct inputs are included. Text output is plain UTF-8 unless user requests Markdown. `AGENTS.md` always emitted; empty for ordinary nodes.

## Pace

A spoken take has a pace, stated in words per minute because that is a number with a meaning outside this program: roughly 110 is deliberate, 150 ordinary, 200 brisk. The take records both the pace asked for and the pace it reached, and the card says both, because a person judging a line by ear needs the number and a request that was missed must not read as if it had been met. Every spoken take states the pace it speaks at; only a take that was asked for a pace names the request. A pace this voice cannot reach is refused with the limit and the pace the script actually reaches, rather than quietly rendered at some other speed. A line of the script is a sentence: it becomes one phrase with a short gap after it, and blank lines do not create longer pauses, so silence is shaped by how the script is broken into lines rather than by blank space in it.

## Methods that run here, and methods that spend a model

A method is either run by the server or handed to an agent, and the card says which. `plain` writes the prompt verbatim, `readaloud` speaks it with the voice this project ships, `titlecard` draws a picture from it, and `firstcut` turns a linked narration and pictures into a film of scenes; all four are `builtin`, need no account and no network, and are what a new card of each type starts on. Every other method is an agent run, and the card prints that (`sends this card to a model`), the toolbar labels its model settings *for agent cards*, and the press reads **Make** on a built-in card and **Generate** on an agent one, because the two presses differ in what they cost.

A built-in run is a run in every other respect: it claims the card at the press, works in a run directory outside the card, is guarded against damaging the card, freezes its material, publishes under a fresh version, keeps the previous take, and can be stopped. What it does not do is skip the checks. A take must measure as speech and say only words the card was given; a film must have a real video stream, last at least as long as its narration, have an audio track whose samples are not all zero, and carry *the narration it was given* rather than another take's voice - measured by extracting the embedded track and correlating it after accounting for the encoder's delay. A refusal is the card's error with the sentence that says which of those failed, and the take that was already there stays.

A film publishes the composition that rendered it as its script, not a description of the render. The point of a record is that it can reproduce the bytes; a file of comments naming the soundtrack and the length cannot, and the code that decided how the film looks went away with the run directory.

A film is made of scenes, and one linked picture is one scene. Scenes appear in link order, each is shown for as long as the narration speaks while it is on screen, and every cut falls on a phrase boundary the voice actually made - so a change of picture never lands inside a spoken sentence. A scene is captioned with its own words, not with the take's first line. Within a scene the words are shown as **cues**: one per measured phrase, each on screen from the moment its phrase is spoken until the next one starts, so the words on screen are the words being heard rather than one caption left up over three sentences. A cue's reading rate is measured from its own on-screen time, and a film whose words cannot be read at the pace they are spoken - above 20 characters a second - is refused with the cue, the number and the bar in the sentence, rather than published with a number printed beside it. One picture is a film of one scene and needs no phrase times; more than one picture needs a narration whose phrase times were measured, because there is no honest place to cut otherwise, and a film is refused with that reason rather than cut at an even split. A film's pictures are checked the way its sound is: each scene's frame is decoded from the published file and compared with the picture that scene names, so a film showing the first picture for its whole length is refused and named by scene. The card says how many scenes there are, when each is on screen, and the worst picture match. A take made before scenes existed carries no scene record and the card promises nothing about its pictures.

A picture can be made here too (`titlecard`): the server draws one 1280x720 frame from the card's words with no account and no network, which is what lets a film have a second scene without spending a model. Like a film, it publishes the composition that rendered it, and it is measured before publishing - a decodable picture of the size the film will show it in, refused if it came out another size rather than silently stretched.

How a picture sits in the frame is a rule, not a default: a picture within 4% of the frame's shape fills it, and anything further off is shown **whole** with dark bars. Filling a 640x700 portrait into 16:9 took the heads and feet off a real picture, and the person only found out after the film was made. Each scene records the source size, the fit and the fraction of the picture on screen, and the card says it (`640x700 shown whole`), so what a film keeps of a picture is knowable before and after the render. The scene check compares a frame with the pixels its placement says are on screen, which is also what keeps the measurement honest: a picture shown whole with bars is a different crop of the same bytes, not a different picture.Because the shape of a placement changed, the absolute picture floor now applies to every film rather than only to one-picture films - a real two-picture film had published with its scenes measuring 0.282 and 0.580, because "this is the closer of the two pictures" is true of a scene showing neither.

The pace of a first take is set on the card before the press, so it is an intention rather than an instruction to be interpreted; after a take exists the same box describes the bytes and Read again re-reads them.

Quality choices: sketch, demo, standard, artistic, realistic. Sketch and demo omit background unless user explicitly asks for one. Preview displays exact artifact; no preview/final generation mode. Types and methods are filesystem registry entries under `types/<type>/methods/<method>`.
